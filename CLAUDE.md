# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This project is now branded **Hotwheels** (originally "TechSupport", a PHP 8 + MySQL ticketing app). It has been stripped down to a bare skeleton — login, users, profiles/permissions, an administrable menu, and audit logging — as the base for a **car-collection (Hot Wheels) inventory system**, whose data model (catalogs + `tbl_hotwheels_carros` + photo/logo uploads) is now built out under `sistema/cars/` and `sistema/settings/` (see below). Built with plain procedural PHP (no framework, no build step) plus PDO, Bootstrap 5, and vanilla JS. The admin app's root/entry point is `sistema/index.php`, but there's also a **public**, no-login page at the project root — see "Public catalog" below. Nearly all admin code — including `composer.json`/`vendor/` — lives under `sistema/`, which is the actual webroot for the admin app. The only Composer dependencies are `tecnickcom/tcpdf`, `phpmailer/phpmailer`, and `phpoffice/phpspreadsheet` (see [Reference-only screens](#reference-only-screens-tickets-domain) below); everything else is dependency-free.

## Running the app

There is no build, lint, or test command — this is a plain PHP app meant to be dropped onto an Apache/PHP server (XAMPP-style) with `sistema/` as the webroot people actually browse to (`sistema/login.php`, `sistema/index.php`, etc.). The top-level `index.php` just redirects to `sistema/login.php`; the top-level `catalogo.php` is the separate public page (see "Public catalog" below), unrelated to that redirect.

1. Run `composer install` inside `sistema/`.
2. Import `sistema/migrations/database.sql` into MySQL. The dump has its own `CREATE DATABASE IF NOT EXISTS db_hotwheels` + `USE db_hotwheels;` baked in, so it always targets a database literally named `db_hotwheels` regardless of what you pass on the command line — `DB_NAME` in `sistema/config/db.php` must match that name (it does by default for local hosts).
3. Edit `sistema/config/db.php` for local DB credentials.
4. Serve the folder with Apache/PHP (e.g. XAMPP) and open `sistema/install.php` once to create the Master admin user, then delete it.
5. Log in at `sistema/login.php`.

**Windows/PowerShell import gotcha:** never pipe the dump in through PowerShell's text pipeline (`Get-Content database.sql | mysql ...`) — Windows PowerShell 5.1 re-encodes piped text to the console's codepage before it reaches `mysql.exe`'s stdin, silently mangling every accented character even though the file itself and `DB_CHARSET` are correct UTF-8/`utf8mb4`. Import via `cmd /c "mysql -u root --default-character-set=utf8mb4 < migrations/database.sql"` (or the mysql client directly from `cmd.exe`/a real shell) instead, which redirects the raw file bytes untouched. For the same reason, never test-import that file into a *different* database name via `mysql <other_db> < migrations/database.sql` — the file's own `USE db_hotwheels;` statement overrides whatever database you pass on the command line, so it always writes to `db_hotwheels` regardless.

`sistema/migrations/` holds `database.sql` (the full schema dump, regenerate it with `mysqldump` after any schema change), the stale `reset.sql` (truncates tables from the old ticket domain — not updated for the current schema), and dated `database_backup_*.sql` snapshots taken before risky schema changes (gitignored, local only).

Useful ad-hoc checks (no test suite exists):
```
php -l sistema/some_file.php     # syntax check a single file
php -S localhost:8000 -t sistema # quick local server if not using XAMPP/Apache
```

## Architecture

### Request pattern (every screen follows this shape)
Each top-level PHP file under `sistema/` (`usuarios.php`, `perfiles.php`, `cnf_empresa.php`, etc.) is a self-contained MVC-in-one-file script:
1. `require_once __DIR__ . '/includes/auth.php'` (starts session, connects PDO via `config/db.php`) and `includes/functions.php`.
2. `requerirPermiso(ID)` — guards the whole page with the numeric `tbl_menu_admin.id` for *that specific screen* (hardcoded per file, e.g. `requerirPermiso(4)` in `usuarios.php`). There are no `MENU_*` constants — ids are passed literally.
3. Inline handling of POST (`$_POST['accion'] === 'guardar'`) and GET actions (e.g. `?toggle=ID`) before any HTML is emitted, using `redirigirConMensaje()` (PRG pattern: redirect with `?msg_tipo=&msg=` query params, rendered by `mostrarAlertas()`).
4. Query data, then `include __DIR__ . '/includes/header.php'` (opens `<html>`, sidebar, topbar), page HTML, `include __DIR__ . '/includes/footer.php'` (closes tags).
5. Uses `$tituloPagina` (page title / topbar heading) and `botonVolverMenu()` (shows a "back" button when arrived via `?padre=ID` from `menu_opciones.php`).

`sistema/includes/functions.php` holds shared helpers: permission checks (`tienePermiso`, `requerirPermiso`), formatting (`formatoFecha`, `limpiar` for XSS-safe output), and audit logging (`registrarAuditoria` → `tbl_general_auditory`, `registrarEventoAcceso` → `tbl_login`). `sistema/includes/auth.php` has session/login guards (`requerirLogin`) plus `esAdmin`/`requerirAdmin` — admin is defined as having permission on menu id 4 "Usuarios".

### Pagination
Every screen listing records (`cars/carros.php`, `settings/*.php` catalogs, `usuarios.php`, `perfiles.php`, `accesos.php`, `auditoria.php`) uses the same pair of helpers in `functions.php`: `obtenerPaginacion()` reads `$_GET['pagina']`/`$_GET['por_pagina']` (page size whitelisted to `OPCIONES_POR_PAGINA` = 25/50/100/200, default 25) and returns `[$pagina, $porPagina, $offset]`; `renderizarPaginador($totalRegistros, $pagina, $porPagina)` prints the "records per page" `<select>` plus page-number links, preserving every other GET param (search/date filters) in its links — every link is prefixed with `rutaScriptActual()` (the current script's path relative to `sistema/` root, e.g. `settings/colores.php`), not a bare `?query`, for the `<base>`-related reason above. The pattern per screen: run a `SELECT COUNT(*)` with the *same* `WHERE` as the list query first, call `obtenerPaginacion()`, then append `LIMIT $porPagina OFFSET $offset` (interpolated directly — both values are already validated against a fixed whitelist, which also sidesteps a real PDO+MySQL gotcha: binding `LIMIT`/`OFFSET` as `?` params fails under native prepared statements, and `PDO::ATTR_EMULATE_PREPARES` is `false` in `config/db.php`). `menus.php` is deliberately excluded — it's a small drag-to-reorder list, and paginating it would split the reorderable set across pages.

### Permissions & menu model
- `tbl_menu_admin` rows are menu options; each has an `id`, `orden`, `icono`, `url`, and `is_submenu` (0 for top-level, or the parent's id for a child).
- `tbl_profiles.permisos` is a CSV of `tbl_menu_admin.id`s; on login these are exploded into `$_SESSION['tsp_permisos']` (see `login.php`).
- A menu option with children never links directly to its `url` — the sidebar routes it to `menu_opciones.php?padre=ID`, a generic grid screen that lists only the child options the current profile is allowed to see.
- Every protected screen re-validates its own permission id server-side via `requerirPermiso()`; the sidebar only controls visibility, not access.
- Current menu tree: `Dashboard` (id 1), `Carros` (34, top-level, list+detail under `cars/`), `Configuración` (9, parent) → `Datos de la Empresa` (10), `Menús` (6), `Perfiles` (5), `Usuarios` (4, ⚠️ don't renumber — `esAdmin()` hardcodes this id), `Configurar Correo` (20), `Config. Carros` (27, parent) → `Colores` (28), `Escalas` (29), `Fabricantes` (30), `Marcas` (31), `Series` (32), `Tipos` (33); `Supervisor` (15, parent) → `Accesos al Sistema` (8), `Auditoría` (7).
- **Menu nesting is normally 2 levels** (top-level → children, via `menu_opciones.php?padre=ID`), but a *child* can itself be a parent (`Config. Carros` under `Configuración` groups the 6 car-catalog screens) — `menu_opciones.php` detects this per-option with `menuTieneHijos($pdo, $op['id'])` and links to itself (`menu_opciones.php?padre=<that option's id>`) instead of the option's own `url` when true. Reuse that same check if you nest another group under an existing one; it composes to any depth since each level re-checks its own children.
- **`sistema/` is usually NOT served at the domain root** — e.g. the actual local Apache `DocumentRoot` is the parent `htdocs`-style folder that hosts several unrelated projects side by side, so the real browsing URL is `http://localhost/hotwheels/sistema/login.php`, not `http://localhost/login.php`. Don't assume otherwise (a prior revision of this doc wrongly did, and hardcoding `<base href="/">` on that assumption broke the entire app's CSS/links, not just the new subfolder screens). Any screen in a subfolder (e.g. `sistema/settings/colores.php`) still needs *some* base-path fix, because the app's asset/link paths (`assets/css/style.css`, `menu_opciones.php`, `logout.php`, etc.) are bare-relative and assume the current page sits directly in `sistema/`. `includes/header.php` computes this itself at request time — it finds `/sistema/` inside `$_SERVER['SCRIPT_NAME']` and uses everything up to and including it as `<base href>` (falling back to `/` if `sistema/` isn't found in the path, e.g. when it *is* served as its own docroot via `php -S -t sistema`). Keep it dynamic like this; don't replace it with a hardcoded path.

  **`<base>` only affects HTML-level relative URLs** (`<a href>`, `<form action>`, `<link>`/`<script src>` rendered into the page) — it does **not** affect a raw HTTP `Location:` redirect header (i.e. `redirigirConMensaje()`), which the browser instead resolves relative to the request URL that produced it. So a screen in `settings/` must pass `redirigirConMensaje()` a *bare* filename (`redirigirConMensaje('colores.php', ...)`, resolves against `settings/` since that's the current request's own directory) while its HTML anchors/forms need the `settings/`-prefixed path (`href="settings/colores.php?toggle=..."`, resolves against the `<base>`-adjusted `sistema/` root) — mixing these up either 404s or, if both get the subfolder prefix, doubles it (`settings/settings/colores.php`). This bit twice: once for `cars/carro_detalle.php`'s own back-link/form/delete-photo anchors (fixed by adding `cars/`), and once for the pagination links below (an `href="?pagina=2"` with no path — query-only — still resolves against the `<base>`-adjusted root, not the current directory, so it silently drops the subfolder too).

### Session keys are prefixed `tsp_`
Every `$_SESSION` key in this app is written as `$_SESSION['tsp_<name>']` (`tsp_usuario_id`, `tsp_nombre`, `tsp_id_tbl_profiles`, `tsp_perfil_nombre`, `tsp_permisos` — set in `login.php`, read across `auth.php`/`functions.php`/`header.php`/`sidebar.php`/every screen). This is a deliberate project convention (not a PHP requirement) meant to namespace the app's session data; keep using the `tsp_` prefix for any new session key.

### Auditing
`registrarAuditoria($pdo, $accion, $tabla, $id_registro, $query = '', $observaciones = '')` is called after essentially every INSERT/UPDATE across the app and writes to `tbl_general_auditory`; it deliberately swallows its own exceptions so a logging failure never blocks the real operation. `$accion` is one of `INS`/`UPD`/`DEL`/`SEL` (`SEL` is reserved for reports, with `$observaciones` holding the report name).
- `$query` must be the **fully interpolated** SQL actually executed (real values, not `?` placeholders) — build it with `interpolarSql($pdo, $sql, $params)`, called with the *same* `$sql`/`$params` just passed to `$stmt->execute()`. It quotes strings via `$pdo->quote()`, leaves numbers/bools unquoted, and renders `null` as `NULL`; never use it to build SQL to execute, only for the audit trail. Leave `$query` as `''` (stored as `NULL`) when the action has no single representative SQL statement — put a description in `$observaciones` instead.
- `$observaciones` is a short human-readable description of the task performed.

Login/logout events go to `tbl_login` via `registrarEventoAcceso()` instead (unrelated to `tbl_general_auditory`).

### Emailing (`includes/email.php`)
`enviarCorreo($pdo, $datos)` sends mail via `PHPMailer` (Composer, SMTP mode) and is the only way the app sends email. It always reads its connection settings from the single active row in `tbl_email_config_sender` (`ml_host`, `ml_username`, `ml_password`, `id_tbl_email_config_port`/`_auth`/`_scrt` — FKs to the `tbl_email_config_port`/`tbl_email_config_auth`/`tbl_email_config_scrt` lookup tables), editable at `cnf_email.php` (permission id 20, "Configurar Correo"). `$datos['cc']`/`['bcc']` fall back to the config row's own `cc`/`bcc` when not passed explicitly.

Every call — success or failure — writes one row to `tbl_email_send` (`state = 1`/`comment = 'OK'` on success; `state = 0`/`comment` = the PHPMailer/SMTP error on failure) and a matching `tbl_general_auditory` `INS` entry; this logging happens inside `enviarCorreo()` itself. There is currently no active caller of `enviarCorreo()` — the only one that existed (`soporte_email.php`) is a reference-only screen, see below.

### Reference-only screens (tickets domain)
Four files were deliberately **left in place but not wired into the menu** when the ticket/client/payment domain was removed, as copy-from templates for whenever the car-inventory data model is designed: `soporte_email.php`, `importar_soportes.php`, `soporte_pdf.php`, and `includes/soporte_pdf_builder.php`. They still reference tables that no longer exist (`tbl_soportes`, `tbl_clientes`, `tbl_saldos`, the `tbl_soporte_*` catalogs) and **will error if invoked** — that's expected. A few `functions.php` helpers survive only because these files still call them: the `ESTADO_SOPORTE_*` constants, `generarNumeroTicket`/`incrementarNumeroTicket` (and the matching `prefijo_ticket`/`siguiente_numero` columns on `tbl_configuracion`, still editable from `cnf_empresa.php`), `resolverRutaArchivoSoporte`, and `recalcularSaldoCliente`. Don't delete these without also deleting (or rewriting) the four files above.

They demonstrate three patterns worth reusing once the car model exists: emailing a generated PDF as an attachment with per-record send-count tracking (`soporte_email.php` + `soporte_pdf_builder.php`, via `tbl_email_send`), building a PDF with TCPDF including a rotated watermark (`includes/soporte_pdf_builder.php`'s `marcaDeAgua()` — note its `GetX()`/`GetY()` save-and-restore around `Text()`, needed because TCPDF's `Text()` moves the page cursor even inside a `StartTransform()` rotation block), and bulk-importing rows from a named-header `.xlsx` file with phpspreadsheet, validating/resolving each row before insert (`importar_soportes.php`).

### Car inventory catalogs (`sistema/settings/`)
The emerging car-collection data model lives in tables prefixed `tbl_hotwheels_` (imported/managed outside this app's migrations — table set has been changing as the model is worked out, so don't assume the list below is exhaustive; check `SHOW TABLES LIKE 'tbl_hotwheels_%'` before relying on it). `sistema/settings/` holds simple create/edit catalog screens for the lookup tables — `colores.php`, `escalas.php`, `fabricantes.php`, `marcas.php`, `series.php`, `tipos.php` — following the same self-contained-screen pattern as the rest of the app (just `require_once __DIR__ . '/../includes/...'` instead of `__DIR__ . '/includes/...'` since they're one level deeper). Each catalog table is `id` (PK), `nombre` (`colores` also has `hexcol`), `user_ing`/`fecha_hora_ing`, `state` — no `orden` column, so unlike the old ticket catalogs these lists don't support drag-reorder, just sort by `nombre`. `tbl_hotwheels_carros` (the actual inventory rows) has FK-style columns named after their target table (`id_tbl_hotwheels_marcas`, `id_tbl_hotwheels_colores`, etc.). These tables are MyISAM/`latin1`, unlike the rest of the schema (InnoDB/`utf8mb4`) — a pre-existing mismatch from how they were imported, not something screens should try to paper over.

`marcas.php` additionally manages a single brand logo per row, stored **without a DB column** — the filename is fully deterministic (`files/marcas/folder_{id}/fot_{id}.jpg`, thumbnail `.../thumbnail/s_fot_{id}.jpg`), so `resolverRutaLogoMarca()`/`resolverRutaMiniaturaLogoMarca()` (`functions.php`) just `file_exists()`-check that fixed path rather than reading a filename from a table, and `procesarLogoMarca()` always overwrites in place (one logo per marca, no sequential numbering like the car photos). The list's "Logo" column is a clickable thumbnail/placeholder (`<label>` wrapping a `d-none` `<input type="file">`) whose `onchange` calls `subirLogoMarca(this, idMarca)` — a `fetch()` POST (`accion=subir_logo`, built as `FormData` so it carries the file) to `rutaScriptActual()`, **not** a real form submit, so the page never reloads. The `subir_logo` branch responds `Content-Type: application/json` (`{"ok":true,"ruta":...}` or `{"ok":false,"mensaje":...}`) instead of `redirigirConMensaje()`-ing like every other action in this app; on success the JS swaps the `<span id="logoMarca{id}">`'s `innerHTML` for a new `<img>` pointing at `data.ruta` with a `?t=<timestamp>` cache-buster (the filename never changes on re-upload, so without it the browser would keep showing the stale cached image), and shows the result via `mostrarAviso()` (from `app.js`, already loaded through `footer.php`) instead of the page-level alert `mostrarAlertas()` renders from `$_GET['msg']`. `sistema/files/marcas/` already had logos for the existing brands *before* this screen existed (pre-populated externally, same as `files/carros/` before `cars/` was built) — already in this exact `fot_{id}.jpg`/`s_fot_{id}.jpg` shape, so no backfill was needed here (unlike the cars photos, there's no separate table row to backfill; file presence alone drives display).

### Car inventory records (`sistema/cars/`)
`carros.php` (list, with a `buscar` text filter on modelo/internalcode/marca) and `carro_detalle.php` (create/edit, both permission id 34) manage `tbl_hotwheels_carros` itself. Unlike the `settings/` catalogs this entity has a photo gallery, so list and detail are two files rather than one, matching the old ticket app's `soportes.php`/`soporte_detalle.php` split. Creating a new car and attaching photos both happen in the same multipart POST to `carro_detalle.php` — the insert runs first to get the new id, then `procesarArchivosAdjuntosCarro()` uses it, exactly like the old `soportes.php` did for `soporte_id`.

`carros.php`'s photo thumbnail is clickable when the car has any photos — it embeds that car's full gallery as inline JSON in the `onclick` (`onclick='abrirGaleria("modelo", [{archivo,miniatura}, ...])'`), the same "pass the row as JSON to a JS function" pattern the catalog screens use for their edit forms (e.g. `editarColor(<?= json_encode($c) ?>)`); `abrirGaleria()` in the page's own `<script>` fills a shared Bootstrap modal (`#modalGaleria`) with the model name as title and a thumbnail grid, falling back to the full image when a thumbnail is missing. There's no AJAX endpoint for this — the gallery data for every car on the current (paginated) page is fetched once up front, which is only safe because pagination already bounds it to at most 200 cars per page.

`carros.php`'s list renders **twice** — once as the `<table>` (`.table-responsive.d-none.d-md-block`, so hidden below the `md` breakpoint) and once as stacked cards (`.ficha-item` rows, `.d-md-none`, so hidden at `md` and up) — both always in the DOM, CSS/Bootstrap utility classes pick which one shows. Both loops duplicate the same small per-row computation (thumbnail, gallery JSON); that's deliberate given this app's "no premature abstraction" convention, not an oversight. `.ficha-item`/`.ficha-chip`/`.ficha-foto` (in `style.css`) are the shared building blocks for any future "table on desktop, cards on mobile" screen — reuse those class names rather than inventing new ones per screen.

`carro_detalle.php` has this app's first small JSON GET endpoint: `?verificar_modelo=<texto>&id=<id>` (guarded by the same `requerirPermiso(34)` as the rest of the file, checked *before* the `isset($_GET['verificar_modelo'])` branch) returns `{"existe": true|false}` — a case-insensitive (`LOWER(modelo) = LOWER(?)`) duplicate check excluding the record's own id, so editing a car doesn't flag its own model. The "Modelo" field's `input` listener (debounced 400ms, in the page's closing `<script>`) calls it via `fetch()` and toggles a warning line under the field; it's purely informational, never blocks saving, since a real collection can legitimately have the same casting name released multiple times (different colors/years). The fetch URL is built from `rutaScriptActual()` (`cars/carro_detalle.php`), not a bare filename — `fetch()` resolves relative to the `<base>`-adjusted document root exactly like `<a href>`, so the same subfolder gotcha documented above applies to it too.

### Public catalog (`catalogo.php`, project root)
A single self-contained, **no-login** page — deliberately outside `sistema/` (it's a showcase page, not an admin screen, and living at the project root means it isn't subject to the `<base href>` subfolder gotcha documented above at all: every asset path in it is written relative to *this* file's own location, one level above `sistema/`). It opens `sistema/config/db.php` directly (skips `auth.php`/sessions entirely — no login is required or checked) and re-implements its own tiny `rutaFotoCarro()`/`rutaMiniaturaCarro()`/`rutaLogoMarca()`/`rutaMiniaturaLogoMarca()` path helpers (prefixed `sistema/...`) rather than reusing `includes/functions.php`'s versions, which assume they're called from inside `sistema/` — this is a deliberate boundary between the public page and the admin app, not an oversight; don't "deduplicate" it by pulling in `sistema/includes/`.

It groups every active car (`state=1`) by `id_tbl_hotwheels_marcas` into one section per brand (brand logo + name + count, sorted alphabetically), each with a responsive card grid; cars with no marca assigned land in a trailing "Sin marca asignada" section rather than being silently dropped — the hero's total-cars stat must equal the sum of every rendered card, and it doesn't if that section is ever removed. All 330+ cars render server-side in one request (no pagination) — deliberate for a single-owner showcase catalog at this size, but revisit with real pagination (reuse `obtenerPaginacion()`'s approach) if the collection grows an order of magnitude. Search (`#inputBuscar`) and the "jump to brand" chip nav are both pure client-side (a `data-buscar` string per card, `data-marca-nombre` per section, hide/show via a plain substring match) since the whole dataset is already on the page — no fetch, no backend endpoint. The photo click handler (`abrirLightbox()`) is a minimal single-image lightbox, intentionally simpler than the admin gallery modal (`carros.php`'s `abrirGaleria()`) since this page shows one photo per card (the car's first/`portada` photo) rather than the full per-car gallery.

Photo uploads (`tbl_hotwheels_carros_archivos`: `id_tbl_hotwheels_carros`, `archivo`, `nombre_original`, `state`, `user_ing`, `fecha_hora_ing`) only accept png/jpg/jpeg and always convert to jpg (PNG transparency flattened to white, since JPEG has no alpha) via `guardarImagenJpgConMiniatura()` in `functions.php` — a generic (path-only) helper, re-added there after being removed during the tickets-domain cleanup; re-check `functions.php` before assuming it's missing. Files land in `files/carros/folder_{id}/foto_{n}_{id}.jpg`, thumbnail `files/carros/folder_{id}/thumbnail/s_foto_{n}_{id}.jpg` — `{n}` is a per-folder sequential count (`count(glob('foto_*.jpg')) + 1`), **not** tied to the DB row id, so it stays correct even if a photo is later deleted. `resolverRutaArchivoCarro()`/`resolverRutaMiniaturaCarro()` build the display paths (the latter returns `null` if the thumbnail is missing — some pre-existing photos on disk predate thumbnail generation, see below). Deleting a photo (`carro_detalle.php?id=X&eliminar_archivo=Y`) soft-deletes the row (`state=0`) and unlinks both files, mirroring the old ticket-attachment delete flow.

**Pre-existing files predate this table.** `files/carros/folder_*/` already held hundreds of photos (migrated from elsewhere) before `tbl_hotwheels_carros_archivos` existed; a one-time backfill script inserted a row per existing `foto_*.jpg` (skipping `folder_335`, which has no matching `tbl_hotwheels_carros` row — leftover from before, including a `.mp4` this app never handled). About 200 of those pre-existing photos have no thumbnail on disk; the gallery falls back to the full image for those rather than erroring.

### Dashboard charts (`index.php`)
The three pie charts ("Autos por Marca/Serie/Tipo") use Chart.js (CDN, `chart.js@4.4.4`, no build step) with a fixed 5-color categorical palette (`#2a78d6 #eb6834 #1baf7a #eda100 #e87ba4`) plus a neutral gray (`#898781`) reserved for an "Otras" slice. Each query takes the top 5 by count (`GROUP BY ... ORDER BY n DESC LIMIT 5`) and a separate count folds everything else into "Otras" — never render every distinct marca/serie/tipo as its own slice (there are dozens), and never generate a 6th+ hue for them. Follow this same top-5-plus-Otras shape for any future breakdown-by-category chart on this dashboard.

### Frontend
No JS build step — Bootstrap 5 and Bootstrap Icons are loaded from CDN in `includes/header.php`/`login.php`, plus local `assets/css/style.css` and `assets/js/app.js`. The searchable icon picker (`inicializarSelectorIcono()` in `assets/js/bootstrap-icons-list.js`) is still active, used by `menus.php` to pick each menu option's icon. `assets/js/app.js` also still contains drag-and-drop catalog reordering (left over from the removed ticket screens, currently unused — safe to reuse or delete) and a file dropzone (`inicializarDropzone()`), which **is** active again: `cars/carro_detalle.php` reuses it for car photo uploads.

### Visual theme
An automotive/collector theme (dark carbon + racing red + amber-gold accents), replacing the original blue/orange "TechSupport" look. Everything lives in CSS custom properties at the top of `assets/css/style.css` (`--carbon-oscuro`, `--carbon-medio`, `--rojo-principal`, `--rojo-oscuro`, `--ambar`, `--ambar-claro`, `--plata`, `--crema`, `--crema-calida`, `--texto`) — change the theme by editing those, not the individual rules below them. `--rojo-principal` is the "brand" accent used almost everywhere the old `--azul-principal` was (`btn-tsp`, `text-tsp`, panel titles, active nav); `--carbon-oscuro`/`--carbon-medio` are the sidebar's dark gradient, decoupled from the brand accent on purpose so the sidebar reads as neutral charcoal rather than red. The brand name uses Google Fonts' **Playfair Display** (loaded via `<link>` in `includes/header.php` and `login.php`, not `@import` in the CSS, for load-order reasons) for a more elegant serif touch on `.sidebar-brand .brand-text` and `.login-box h4`; body text stays the system sans.

`assets/img/logo.svg` (the circular car-badge mark shown in the sidebar and login page) and the PWA/favicon raster set (`icon-192.png`, `icon-512.png`, `apple-touch-icon.png`, `favicon.ico`) were all hand-drawn to the same design — a car silhouette (cream body + red racing stripe + red-hub wheels) inside a dark badge with an amber ring — so keep them in sync if the mark changes. There's no Imagick on this box, only GD, which can't rasterize SVG directly or write `.ico`; the PNGs were produced by re-drawing the same shapes at each target size with GD primitives (rounded rects via `imagefilledrectangle` + corner `imagefilledellipse`, the amber ring via a filled ambar circle with a smaller carbon circle on top rather than a stroked outline — outlined ellipses render visibly rough at large sizes in GD), and `favicon.ico` is a hand-built ICO container (a plain 6-byte header + one 16-byte directory entry per image + the raw PNG bytes appended — the modern "PNG-in-ICO" form, valid since Vista) wrapping 16/32/48px PNGs of the same drawing. Don't try to regenerate these by pointing GD at the SVG; there's no SVG rasterizer available — redraw with the same primitive-based approach instead. `assets/img/logo_*.png` are unrelated: user-uploaded company logos from `cnf_empresa.php`, referenced by `tbl_configuracion.logo` — not part of this app-level branding.
